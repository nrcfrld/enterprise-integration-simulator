## Critical

### C5 — A frontend on port 5174 cannot complete login

**Excluded after audit:** user retains frontend origin 5173. No CORS, Vite or Playwright change is requested or implemented.

**Problem:** The API permits only `http://localhost:5173` and `http://127.0.0.1:5173`. The user's frontend origin is `http://localhost:5174`, so the JSON login preflight receives no `Access-Control-Allow-Origin`. Compose already reserves host port 5173; the Vite configuration does not pin a strict port or provide a same-origin API proxy. The exact reason this instance uses 5174 was not independently measured. Changing Playwright's `MARKETPLACE_ADMIN_URL` changes the test destination, not the API allowlist or frontend server port.

**Why it matters for juniors:** This blocks the first step in that local-development configuration, before credentials can be checked. A generic fetch error encourages debugging passwords or API health instead of the origin mismatch. It is not a claim that login fails on the supported 5173 origin.

**Affected:** Local Admin login, public requests in the browser simulator, development setup and troubleshooting.

**Recommended improvement:** Establish one documented development-origin contract: either pin the supported port with a clear occupied-port error, use a same-origin development proxy consistently for console and simulator requests, or configure an explicit API origin allowlist. Explain Compose plus local-dev coexistence and provide a preflight troubleshooting check. Test both the configured allowed origin and a rejected origin. Do not use an unrestricted wildcard as a convenience fix.

## High Priority

### H12 — “Run this exact request” exports a different request and omits diagnostic headers

**Implemented after audit — 2026-09-09:** Prepared request inputs now drive edited Node export and outgoing request evidence. Credential secrets use environment placeholders/redaction; response replay/retry/quota headers, HTTP/API errors and raw body evidence are visible.

**Problem:** The Node example receives only endpoint metadata: it substitutes `replace-with-id`, uses the default body, omits edited query values and generates a fresh mutation key. The URL preview omits Tokopedia's generated signing parameters; there is no full prepared outgoing request snapshot. Response display selects quota headers only, hiding useful retry/idempotency/correlation evidence. HTTP errors are displayed under the same completed state as success. Tokopedia's exact signing input contains the secret as part of the algorithm, so copying that raw disclosure is not a safe request export.

**Why it matters for juniors:** A request that succeeds in the simulator can fail when copied, and they cannot confidently explain a retry or distinguish an HTTP rejection from a transport failure. The “exact” label overstates what the example reproduces.

**Affected:** Request Simulator, generated Node examples, response/error inspection.

**Recommended improvement:** Produce the preview, outgoing request and export from one prepared request model containing the edited method, path, query, body and retry identity. Export secrets through environment placeholders and make any sensitive signing-input disclosure explicit. Show HTTP/API failures with recovery guidance, and include supported request ID, Retry-After and Idempotent-Replayed headers. Align the API's CORS exposed-header list as needed.

**Evidence:** [request construction/output](/Users/enrico/Documents/engineering-challenge/apps/marketplace/admin/src/features/developer-portal/components/RequestSimulator.tsx:29), [metadata-only code generation](/Users/enrico/Documents/engineering-challenge/apps/marketplace/admin/src/features/developer-portal/lib/nodeExample.ts:5), [exact-request claim](/Users/enrico/Documents/engineering-challenge/apps/marketplace/admin/src/features/developer-portal/components/CodeExamples.tsx:12).

### H13 — Defaults and draft/reset behavior make first requests and retries unreliable

**Implemented after audit — 2026-09-09:** Useful unfiltered defaults, receiver callback addresses, in-memory operation drafts, original-request retries/new operations, timeout/cancel/reset isolation, credential guards and provider result/page handoffs are implemented.

**Problem:** Tokopedia order search defaults to `ON_HOLD`, excluding fresh UNPAID and seeded COMPLETED orders. Product search defaults to `mug`, which need not match the learner's catalog. Callback examples use example.com. Most body help remains in Reference while Try validates only JSON syntax. Changing operation or leaving Try unmounts its local draft; there is no per-operation draft history. Reset is enabled while a request is pending, clears the result and changes the idempotency key without cancelling or invalidating the pending fetch; that old response can later repopulate the reset screen. There is no elapsed-time, cancel or configurable timeout exercise. Shopee has a list-to-detail order handoff; Tokopedia remains manual copy/paste.

**Why it matters for juniors:** Empty results look like a bad setup. A documentation detour loses edits. A retry may become a new mutation, and a late response can be attributed to the currently displayed inputs. This is distinct from the fixed cross-shop response handling.

**Affected:** Operation picker, Try request form, default examples, reset and timeout/idempotency exercises.

**Recommended improvement:** Start list/search without restrictive filters or supply clearly named fixture presets. Show required body fields, enums and constraints beside the editor. Preserve drafts and retry keys per operation in memory, with explicit “Retry same operation” versus “New operation.” During reset, either block the action or cancel/invalidate the old request and explain that cancellation does not prove a mutation was undone. Add elapsed time and timeout controls. Extend returned-ID and next-page handoffs to both providers; link callback inputs to the working receiver example.

**Evidence:** [Tokopedia defaults](/Users/enrico/Documents/engineering-challenge/apps/marketplace/admin/src/features/developer-portal/data/endpoints.ts:215), [local state/reset/fetch](/Users/enrico/Documents/engineering-challenge/apps/marketplace/admin/src/features/developer-portal/components/RequestSimulator.tsx:51), [keyed simulator and conditional Try](/Users/enrico/Documents/engineering-challenge/apps/marketplace/admin/src/features/developer-portal/DeveloperPortal.tsx:46), [historical COMPLETED fixtures](/Users/enrico/Documents/engineering-challenge/apps/marketplace/internal/server/control_shops.go:225).

### H14 — Pagination hides registrations and choices, and can remove shop context

**Implemented after audit — 2026-09-09:** Shop/picker collections exhaust pagination, choices are filterable, selected shop/provider survive navigation/reload, Webhooks has true totals and paging, and the product query cap is removed. Local tests pass; the approved SQLc regeneration succeeded and produced identical bindings. The earlier approval block is resolved.

**Problem:** The global shop list fetches its first page only. The Shops table itself has pagination, but selecting an existing shop on a later page passes only its ID; that row is not merged into the global shop collection. Resource requests can therefore target that ID while the selector/provider/portal cannot resolve `selectedShop`. Webhooks fetches one default page and has no paginator, while its new overview calls `hooks.length` the number of registered endpoints. Product/warehouse pickers request at most 100 without continuing through pages. The backend control product list also caps its source query at 1,000 before presenting pagination. The package order picker already follows all pages and should be preserved.

**Why it matters for juniors:** A known shop or product appears missing; the 21st webhook may remain active without being visible or editable. Page-only counts look like totals. Later-page shops can lose the provider guidance that otherwise works correctly.

**Affected:** Current shop selector, Shops → use shop, Webhooks summary/list, product/order/inventory pickers, large product catalogs.

**Recommended improvement:** Make selection and list paging end-to-end: hydrate the selected shop object regardless of page, add webhook pagination with true total/enabled-count semantics, and use paged/searchable pickers. Remove hidden backend caps or expose explicit truncation. Test the 21st shop/webhook, 101st product/warehouse, and larger product catalogs; retain shop context through navigation and reload.

**Evidence:** [first-page shop state](/Users/enrico/Documents/engineering-challenge/apps/marketplace/admin/src/features/control-plane/hooks/useControlPlaneResources.ts:65), [ID-only selection](/Users/enrico/Documents/engineering-challenge/apps/marketplace/admin/src/features/control-plane/ControlPlaneApp.tsx:120), [webhook counts](/Users/enrico/Documents/engineering-challenge/apps/marketplace/admin/src/features/control-plane/components/WebhookSettings.tsx:32), [backend default page size](/Users/enrico/Documents/engineering-challenge/apps/marketplace/internal/server/provider_webhooks.go:190), [picker limits](/Users/enrico/Documents/engineering-challenge/apps/marketplace/admin/src/features/control-plane/components/ControlForm.tsx:159), [catalog cap](/Users/enrico/Documents/engineering-challenge/apps/marketplace/internal/server/control_inventory.go:23).

### H16 — A generated Shopee webhook secret is easy to lose during receiver setup

**Implemented after audit — 2026-09-09:** Generated Shopee webhook secrets now use a copy/acknowledgement dialog with protected dismissal, shop/endpoint context and provider-correct receiver/replacement guidance. Tokopedia keeps app-credential verification.

**Problem:** API credentials use a dedicated copy/acknowledgement dialog; a generated Shopee webhook secret is embedded in a generic success notification. It has no dedicated copy or saved-value acknowledgement flow and is lost on dismissal, replacement by another notice, or workspace navigation. The list and edit API correctly do not return the stored secret. This is not a claim that the notice auto-dismisses on a timer. Tokopedia verification uses an app credential and should not be taught to use this registration secret.

**Why it matters for juniors:** The natural next action is to open documentation or receiver setup; doing so can discard the one value required to verify Shopee deliveries. Recovery requires explicitly replacing the webhook secret and updating the receiver.

**Affected:** Admin webhook creation, one-time-value handling, receiver setup/recovery.

**Recommended improvement:** Reuse the one-time credential pattern for Shopee webhook secrets: label shop and endpoint, provide copy, require deliberate acknowledgement, and explain loss/rotation recovery. Provide provider-correct receiver setup instructions in that handoff. Keep secrets out of URLs and durable browser storage.

**Evidence:** [secret-to-notice branch](/Users/enrico/Documents/engineering-challenge/apps/marketplace/admin/src/features/control-plane/components/ControlForm.tsx:323), [credential-only dedicated dialog](/Users/enrico/Documents/engineering-challenge/apps/marketplace/admin/src/features/control-plane/ControlPlaneApp.tsx:146), [notice dismissal](/Users/enrico/Documents/engineering-challenge/apps/marketplace/admin/src/features/control-plane/components/ControlPlaneChrome.tsx:129), [one-time backend return](/Users/enrico/Documents/engineering-challenge/apps/marketplace/internal/server/control_webhooks.go:55).

### H17 — The inventory editor can preserve a stale saved count after refresh

**Implemented after audit — 2026-09-09:** Saved drafts are cleared, clean inputs follow refresh, unsaved stock conflicts are explicit and require review, and pending Save/Add actions prevent duplicate submissions.

**Problem:** After Save, `inventoryDrafts[productID]` retains the submitted physical count. Subsequent data refresh changes the table's on-hand value but the input still prefers that retained draft. Example: save 10; an external carrier action ships 2; refresh the open detail. The table can show 8 while the input remains 10. Pressing Save again replaces physical stock with 10. There is no dirty/conflict indication or pending guard on these row mutations. This is a source-supported risk, not a newly executed concurrent-stock experiment.

**Why it matters for juniors:** The UI can make a saved value look current and silently reintroduce consumed stock, undermining the inventory accounting lesson. It also behaves differently from other mutation controls that show pending state and prevent duplicate submissions.

**Affected:** Warehouse inventory detail, row Save/Add actions, refreshed editable state.

**Recommended improvement:** Clear the draft after successful acknowledgement; let clean inputs follow refreshed server values. Preserve genuinely unsaved edits with an explicit conflict indicator when server counts change. Disable duplicate row submissions while pending and show the value being saved. Consider version/updated-at checking for deliberate stock-count replacement. Test save → external shipment → refresh → unchanged Save, plus a refresh during an unsaved edit.

**Evidence:** [saved draft retained](/Users/enrico/Documents/engineering-challenge/apps/marketplace/admin/src/features/control-plane/components/details/WarehouseDetail.tsx:60), [draft preferred over current stock](/Users/enrico/Documents/engineering-challenge/apps/marketplace/admin/src/features/control-plane/components/details/WarehouseDetail.tsx:124), [detail refreshed without remounting its editor](/Users/enrico/Documents/engineering-challenge/apps/marketplace/admin/src/features/control-plane/components/DetailPanel.tsx:112).

### H11 — The learning journey still ends before durable external application processing

**Implemented after audit — 2026-09-09:** Dedicated provider-specific durable consumer lessons and downloadable SQLite-backed receiver/worker now cover acceptance, persistence, pagination, stable mutation keys and recovery. See the [runnable lesson](../../apps/marketplace/admin/examples/durable-consumer-README.md).

**Problem:** Lifecycle, inventory, receiver verification and attempt diagnostics are now documented and reachable. However, the local receiver keeps its inbox in memory and logs “fetch current provider state” rather than completing that work. Start Here links to an order list but does not assemble a fresh-order exercise through durable deduplication, state retrieval/persistence, idempotent action retries and reconciliation after delayed/out-of-order events. Pagination conventions exist in reference material but there is no complete provider-specific application loop tying them together.

**Why it matters for juniors:** Receiving 204/DELIVERED proves transport acceptance, not that an OMS has persisted or processed the order correctly. Learners still have to design the most important application-side behavior from scattered descriptions.

**Affected:** Start Here, Orders & fulfilment, Webhooks, Errors & limits, receiver/client examples.

**Recommended improvement:** Publish one guided exercise per provider using a newly simulated UNPAID order. Show exact commands/IDs, durable inbox uniqueness by shop/event, commit before acknowledgement, a worker fetching current provider state, identifier mapping, a real pagination loop, and same-key retry. Include expected evidence for duplicate, restart, delayed/out-of-order and return-to-sender cases. Keep simulation controls distinct from the external app's calls, and label the current in-memory receiver as a learning starter.

## Nice to Have

### N1 — Remaining list labels and columns slow record identification

**Problem:** Products and fulfillment lists now have stable useful columns, but Orders/Credentials/Users still fall back to seven scalar object keys. Timestamps and many IDs remain raw, with limited copy affordances. Package `item_count` is distinct lines rather than units. Warehouse summaries omit dispatch address despite the operations guide saying the page lists it. The order-detail action is called “Event trail” even though it opens the full order.

**Why it matters for juniors:** Learners must open extra screens or infer whether “items” means units, and an event label conceals the primary order-detail destination.

**Affected:** Resource tables, order entry action, package counts, warehouse summary/documentation.

**Recommended improvement:** Use explicit task-oriented columns and named ID copy actions; rename the order action “View order.” Label lines versus units and show compact dates with timezone/exact-value access. Either expose dispatch location in the warehouse list or correct the guide. Retain existing full pagination totals; do not report them as entirely absent.

**Evidence:** [column fallback](/Users/enrico/Documents/engineering-challenge/apps/marketplace/admin/src/features/control-plane/components/ResourcePage.tsx:259), [warehouse guide claim](/Users/enrico/Documents/engineering-challenge/docs/marketplace/operations-guide.md:35).

### N2 — Scenario settings lack a clear exercise and return-to-normal path

**Problem:** Help text mixes Indonesian with English labels/reference material; probability inputs have a minimum but no maximum of 100. There are no named exercises or “clear all faults” action, and Try does not summarize active shop faults. Resetting sample data preserves scenario settings.

**Why it matters for juniors:** A learner may interpret an intentionally failing request as broken authentication, or believe seed reset restored normal behavior. Mixed language adds a barrier for learners who read only one locale.

**Affected:** Scenarios, sample reset, request context.

**Recommended improvement:** Choose a consistent locale, enforce/display ranges, add optional presets with expected observable outcomes and an explicit reset, and show active fault settings beside requests. Make “reset data” and “clear faults” separate concepts.

**Evidence:** [scenario inputs/help](/Users/enrico/Documents/engineering-challenge/apps/marketplace/admin/src/features/control-plane/components/Scenario.tsx:52), [reset semantics](/Users/enrico/Documents/engineering-challenge/apps/marketplace/admin/src/features/control-plane/components/DashboardPages.tsx:145).

### N3 — Lessons and resource details are not durable destinations

**Problem:** Portal section/endpoint selection and detail history remain component state. API Documentation and Integration Guide both navigate to `/docs`; with the portal kept mounted, the guide alias may show the last section instead of Start Here. Event filters are in the URL, but selected shop and page are not, so sharing that URL cannot reliably restore the intended context. Selected navigation is primarily conveyed by CSS rather than `aria-current`/`aria-pressed` in the sidebar and portal.

**Why it matters for juniors:** Bookmarking, mentor sharing, browser Back and assistive-technology orientation do not reliably describe the current lesson or resource.

**Affected:** Sidebar/portal navigation, details, event filter URLs.

**Recommended improvement:** Add durable non-secret shop/section/operation/resource state with normal Back behavior. Give guide and reference links explicit destinations and expose the current selection semantically. Keep credentials and request secrets out of URLs.

**Evidence:** [guide alias](/Users/enrico/Documents/engineering-challenge/apps/marketplace/admin/src/app/navigation.ts:90), [portal state](/Users/enrico/Documents/engineering-challenge/apps/marketplace/admin/src/features/developer-portal/DeveloperPortal.tsx:50), [sidebar active class](/Users/enrico/Documents/engineering-challenge/apps/marketplace/admin/src/features/control-plane/components/ControlPlaneChrome.tsx:38), [event URL filters](/Users/enrico/Documents/engineering-challenge/apps/marketplace/admin/src/features/control-plane/components/EventsPage.tsx:25).

### N4 — Account management remains misplaced or hidden

**Problem:** Request signing includes a live “Try account registration” form even though reaching the portal already requires a console session. Meanwhile, `/users` is implemented but absent from primary navigation, although the operations guide instructs Admins to open Users.

**Why it matters for juniors:** An optional account exercise competes with the integration-authentication task, while mentors cannot easily discover the documented user-management feature.

**Affected:** Request signing, Admin navigation, operations guide.

**Recommended improvement:** Put registration in an explicitly optional Control Plane account reference. Expose Users for Admins, or document a real accessible route. Preserve supported account APIs; do not delete them just because the navigation is incomplete.
